## A. 事実の誤り（このサイトの売りに直接効く）

### A-1. `/coolerbox/erabikata/` のアイキャッチ図が古い　`検証済み`

**収益記事の1枚目の図が、本文と違う数字を出している。**

| | 図（`coolerbox-erabikata-eyecatch.png`） | 本文 |
|---|---|---|
| 見出しの数字 | **26製品**（「内寸を並べた 26製品」） | **33製品**（title・H1・本文に10箇所） |
| 2Lが立つ数 | **306mm以上は 26製品中3つ** | **33製品中9つ。うち6つがコールマン** |

- 図の定義：`tools/figures/figures.py:651` `key="26"` ／ `figures.py:655` `"306mm以上は 26製品中3つ"`
- 本文：`site/content/articles/coolerbox-erabikata.md`（`33製品` が10箇所、`26製品` は**0箇所**）
- PNG を開いて目視でも確認した
- **OG画像 `site/public/img/og/erabikata.png` は「33製品」で正しい。** 記事を26→33製品に広げたとき、
  OG画像だけ焼き直してアイキャッチを直し忘れたと見られる（**この経緯自体は未検証**）

**なぜ検査をすり抜けたか（ここが本題）**

`tools/figures/build.py` の `check_numbers` は、図の数値を **旧SVG** と突き合わせている（`build.py:60-81`）。
つまり「PowerPoint 移行のときに数字を打ち間違えていないか」の検査であって、
**「図が本文と一致しているか」は一度も検査していない。**

さらに数値トークンだけの照合では捕まらない。「26」は本文に **「26Lクラス」** として存在するので、
`26製品` が消えていても素通りする。

⚠️ `CLAUDE.md` の「ビルドが3つ検査して落とす（数値が元図にあるか／…）」は正しいが、
**「元図」＝旧SVG であって本文ではない。** ここを取り違えると「図は検査済み」と誤解する。

## C. 流入：律速が表示回数なら、ここが空いている　`検証済み`

### C-1. カテゴリ3ページの本文が0文字

`/coolerbox/` `/cassette-konro/` `/kyatatsu/` の中身は
**定型1文（「〜について、メーカー公式の寸法から計算して比べた記事です。」）＋記事一覧だけ。**
`<main>` から一覧を除いた固有の本文は**0文字**。

「クーラーボックス 内寸」のような head 語の受け皿になり得る位置なのに、順位を取る材料が無い。
被リンク（内部）は10本入っているので、クロールはされている。

### C-2. BreadcrumbList の構造化データが無い

パンくずのUIは出ている（`aria-label="パンくずリスト"`）が、**JSON-LD には `BreadcrumbList` が1件も無い。**
全27ページを確認した。出しているのは `Article` / `WebPage` / `Organization` / `WebSite` / `CollectionPage`。

`Article` に `author` も無い（`publisher` はある）。

### C-3. 関連記事が「同カテゴリの新着5本」なので、古い記事に何も入らない

`dist/` の被リンクを数えた結果（関連記事ブロック内のみ）：

| ページ | 関連記事からの被リンク |
|---|---|
| `/coolerbox/omosa/`（最新） | **13** |
| `/coolerbox/erabikata/` | 13 |
| `/coolerbox/2l-tateru/` | **0** |
| `/coolerbox/500ml-honsuu/` | **0** |
| `/coolerbox/daiwa-shimano/` | **0** |
| `/coolerbox/horeizai-honsuu/` | **0** |

**古い4本はどの関連記事にも出てこない。** 特に `/coolerbox/500ml-honsuu/` は
（`serp-check.md` で需要が最大とされているキーワードなのに）**本文からの被リンク2・関連記事0**。

日付順で機械的に出しているため、記事が増えるほど古い記事が内部リンクから落ちていく。

### C-4. タイトルが長い

記事タイトルは**39〜56字**（`<title>` の長さ）。モバイルのSERPは全角30字前後で切れるので、
差別化している後半（「同じ180でも天板の高さは10cm違いました」）が落ちる。
**表示回数ではなくCTRの話なので、律速そのものではない。**

## D. 速度・配信　`検証済み`

### D-1. トップページの画像が20枚・1.35MB

1200×630 の PNG を**約150px幅のサムネイル**として20枚出している。合計 1,353KB。
`srcset` は0件。WebP/AVIF も無い。全部 `loading="lazy"`。

そのうえ、150px に縮めた早見表の図は**文字がまったく読めない**（実機で確認）。
容量を払って、読めない絵を出している状態。

### D-2. CSS も画像も `max-age=0`

```
Cache-Control: public, max-age=0, must-revalidate
```

HTML だけでなく `/styles.css` と `/img/*.png` にも付いている（Workers Assets の既定）。
再訪のたびに全アセットを再検証する。`site/public/_headers` は存在しない。

なお HTML は brotli で配信されている（`Content-Encoding: br`）。404 も 404 を返している。

## 直す順番（提案）

1. **A-1**（図の 26 → 33）。サイトの売りが数字の正確さなので、ここだけは性質が違う
2. **B-1 / B-2**（`.pcard` を残り14記事に置く）。未達要件に直接効くのはここだけ
3. **C-1 / C-3**（カテゴリページに本文、関連記事を日付順から変える）。律速の表示回数に効く
4. **C-2**（BreadcrumbList）。`build.mjs` に数行足すだけで済む
5. **D-2**（`_headers`）→ **D-1**（サムネイルを別に焼く）
6. E・F は手が空いたとき

⚠️ **1〜6のうち「効く」と確認できているのは1つも無い。** 2〜3 は
「律速は表示回数」という HANDOFF の測定に基づく推論であって、実測ではない。
9/3〜9/5 の `/measure` の結果を見てから2以降の順番を決め直したほうがよい。
