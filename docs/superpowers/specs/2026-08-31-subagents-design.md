# 作業別サブエージェント／Skill の設計

作成: 2026-08-31 ／ 状態: **設計（未実装）**

## 何を作るか

「寸法で選ぶ」の運営作業を、**手順書（Skill）と役割の分離（サブエージェント）**の2つに分けて固定する。

利用者が選んだ目的は2つ。**文脈の隔離と並列化は目的に入っていない。**

| 目的 | 担当 |
|---|---|
| **手順の再現性**（いつ誰がやっても同じ手順・同じ品質） | **Skill**（手順書） |
| **品質＝生成と評価の分離** | **サブエージェント**（writer / reviewer） |

### 採用しなかった案

| 案 | 却下の理由 |
|---|---|
| 作業5種＋オーケストレーターの6体構成 | `harness-agents-skills.md`「最初からオーケストレーター・ワーカーを設計しない」に反する。**Claude Code ではメインセッションがすでに指示役**なので役目が二重になる。`harness-core.md`「選択肢が多いほど精度は下がる」にも反する |
| ルーティング用 Skill ＋ エージェント4体 | 「指示役が欲しい」は満たすが、**今回の目的2つ（再現性・生成と評価の分離）はどちらも指示役を必要としない**。不要な部品 |

**指示を出す層はメインセッションが担う。専用のエージェントは作らない。**

---

## ファイル構成（7ファイル）

```
.claude/agents/article-writer.md      生成：記事を書く
.claude/agents/article-reviewer.md    評価：記事を落第させる（独立）
.claude/skills/measure/SKILL.md       手順：測定
.claude/skills/link-check/SKILL.md    手順：リンク着地の実測
.claude/skills/fix-site/SKILL.md      手順：サイト・ビルドの修正
specs/article-contract.md             完了基準（二値判定のみ）
specs/article-rubric.md               品質の段階評価
```

`specs/` をリポジトリ直下に置くのは `harness-agents-skills.md` の指定による
（「`src/` と分離しつつプロジェクトルート直下で自然に見つかる」）。

## 1. エージェント2体

### 責務の境界

| | article-writer | article-reviewer |
|---|---|---|
| 役目 | 一次情報収集 → 計算 → 原稿 → **ビルドが通るまで直す** | 契約とルーブリックに照らして**落第させる** |
| 読む spec | `specs/article-contract.md` のみ | **契約とルーブリックの両方** |
| 入力 | テーマ（何を計算して答えるか） | 記事のパス**だけ** |
| tools | `Read, Write, Edit, Bash, Glob, Grep, WebFetch, WebSearch` | `Read, Grep, Glob, Bash, WebFetch` |
| 完了条件 | ビルドが通り、契約の8項目を自分で通してある（reviewer はそれを信用せず再実行する） |
| メインに返すもの | 記事パス／使った一次情報URL一覧／計算の要点／未解決点。**1,000〜2,000トークン** | 二値チェックの合否表／落第項目／段階評価。**1,000〜2,000トークン** |

### ★ reviewer から Write/Edit を外す。ただし完全な強制ではない

**外す理由**: 「直すな」と指示書に書くだけでは確率的にしか守られない
（`harness-core.md`「強制と依頼を使い分ける」「指示書に書いたから安全、とは考えない」）。

⚠️ **これは決定論的な強制ではない。** reviewer はビルドと検査ツールを走らせるために `Bash` が要り、
**`Bash` があればリダイレクトでファイルは書ける。** Write/Edit を外す効果は
**「既定の経路を塞ぐ」ところまで**で、抜け穴は残る。指示書にも「書き換えない」と明記して二重にする。

**より強い強制が要ると分かったときは Hooks で `.claude/hooks/` に落とす。**
いまは入れない（`harness-core.md`「最小から始めて、実測で効果が示されたときだけ足す」）。

### ★ reviewer は writer の返答を見ない

reviewer に渡すのは**記事のパスだけ**。writer がどう考えたか、どこで迷ったかは渡さない。

**理由**: 生成時の文脈と思考パターンが残ると、自己評価と同じ構造的バイアスがかかる
（`harness-agents-skills.md`「生成と評価を分離する」）。

### ★ reviewer は writer の申告を根拠にしない

契約の各項目は、reviewer が**自分でコマンドを実行して**確かめる。
「writer がビルドを通したと言っている」は根拠にしない
（`harness-core.md`「自己評価を品質の根拠にしない」「証拠は画面に出す」）。

## 2. `specs/article-contract.md` — 完了基準（二値のみ）

### ★ ビルドがすでに落としている検査は書かない

`site/build.mjs` が例外を投げて止めるものは、契約に**書かない**。二重化しても判定は増えないため。

| ビルドが落とすもの | 実装 |
|---|---|
| front matter の5項目＋category | `readFrontMatter` / カテゴリ照合 |
| カードの数字とその商品の表の行の不一致 | `assertCardNumbers` |
| 日本語の太字が約物で壊れる形 | `assertNoRawEmphasis` |
| eyecatch と同じ画像が本文にも残る | eyecatch重複チェック（2026-08-31 追加） |
| 引用の直後に空行がなく本文が飲み込まれる | `assertNoLazyBlockquote`（2026-08-31 追加） |
| `[[LINK:...]]` の検索語が空 | `resolveLinks` |

**契約が埋めるのは「ビルドが見ていない穴」だけ。**

### 契約の項目（すべて二値。主観表現を書かない）

| # | 判定 | 確かめ方 |
|---|---|---|
| 1 | ビルドが成功する | `npm run build --prefix site` の終了コード0 |
| 2 | 本文の数値が「数字の出どころ」節の出典URLに紐づく | 節の存在と、本文の主要数値ごとの対応を目視で照合 |
| 3 | 出典URLがすべてメーカー公式ドメイン | 通販サイト・まとめ記事のドメインが**0件** |
| 4 | 計算値を「実測」と書いていない | 「実測」を全文検索し、各出現が実際に測った値か確認 |
| 5 | 価格・在庫・送料に触れていない | `価格` `在庫` `送料` `セール` `割引` `安い` `¥` を全文検索して0件。`円` も検索するが**`楕円` `円筒` `円形` は誤検出**なので、ヒットごとに価格の話か判定する |
| 6 | 未検証の主張に「未検証」と明記されている | 一次情報で確認できなかった記述に印があるか |
| 7 | 最初のアフィリエイトリンクが本文の20%以内 | `python tools/check-link-position.py` に当該記事が超過として出ない |
| 8 | 表の計算値が独立に再現できる | reviewer が表の計算値を**1つ以上選んで自分で計算し直し**、一致する |

⚠️ **1件でも不合格なら落第。** 段階評価の高さで買い戻せない
（`harness-agents-skills.md`「クリティカル項目が1つでも不合格なら問答無用で続行」）。

⚠️ **2・4・5・6・8 は、検索そのものは機械的だが、ヒット1件ごとの判定に読解が要る。**
だから **reviewer は不合格の項目について「ファイル名:行番号」と該当箇所の引用を必ず出す**。
出せないものは不合格にしない。**これが「二値で判定できる」の担保**であって、
判定理由を書かずに「怪しい」で落とすことは認めない。

## 3. `specs/article-rubric.md` — 段階評価

**落第の判定には使わない。** 良し悪しの方向を示すだけ。

| 観点 | 見るところ |
|---|---|
| 問いと答えになっているか | タイトルと各 `##` が「問い」で、直後に数字の答えが出ているか |
| カタログにない数値を答えているか | `docs/serp-check.md` の「勝てるのはカタログに載っていない数値だけ」に合致するか。**サイズ・型番・規格の解説に寄っていないか** |
| 図版1枚で結論が言えるか | eyecatch を単体で見て、記事の結論が分かるか |
| 表が読み切れる幅か | セルが `white-space: nowrap` なので、リンク文言の重複で横幅が膨らんでいないか |
| 導線 | 集客記事なら収益記事へ、収益記事なら製品カードへ、たどれるか |

## 4. Skill 3本

書き方は `harness-agents-skills.md` に従う。フロントマターに `name` / `description`、
本文はステップバイステップ、**曖昧さゼロ・前提条件と完了条件・失敗時の対処**を明記する。

### `/measure` — 測定

手順の原型は 2026-08-31 の実作業（`docs/measurement-2026-08-31.md`）。

1. GSC の検索パフォーマンス（表示・クリック・順位）を読む
2. ページ別・クエリ別を読む
3. サイトマップの最終読み込みとインデックス状況を抜き取りで確認
4. アソシエイト・セントラルのクリック・注文・紹介料を読む
5. `docs/measurement-YYYY-MM-DD.md` に書く
6. `HANDOFF.md` の該当節を**書き直す**（継ぎ足さない）

**手順に埋め込む罠**（どれも実際に踏んだ・踏みかけたもの）:
- ⚠️ **同じURLにインデックス登録を再送信しない**（順番も優先順位も変わらない）
- ⚠️ **GSCのデータは3日遅れている。** 「今日の数字」ではない
- ⚠️ **アソシエイトのクリック数を CTR の分子に使わない。** 自分の確認と切り分けられない
- ⚠️ **標本が小さいうちはクリック0からCTRを判定しない。** 期待クリック数と、0回になる確率を先に出す

**完了条件**: `docs/measurement-YYYY-MM-DD.md` が存在し、前回との差分表があり、HANDOFF が更新されている。

### `/link-check` — リンク着地の実測

手順の原型は `docs/link-check-2026-08-31.md`。

1. 本番の `sitemap.xml` から全ページを取得し、リンクを機械検査（本数・ホスト・`tag=`・`rel`・プレースホルダ）
2. アソシエイト・セントラルでクリックが記録されているかを見る
3. 検索語を Amazon で引いて着地順位を測る
4. 判定は ◎（1位）／○（2位以内）／△（3位以下・親出品・PR過多）／✗（誤った商品）
5. 変更するなら**代替の検索語を実測してから**適用する

**手順に埋め込む罠**:
- ⚠️ **`tag=` を外したURLで測る。** タグ付きで開くとアソシエイトのクリック数に自分の確認が積み上がる
- ⚠️ **一律のルールは使えない。商品ごとに測る**（2026-08-26 のアルインコ、2026-08-31 の達人スリムβで悪化を確認）
- ⚠️ **bash の出力に出た日本語をそのままクエリに使わない**（cp932 で化ける。2026-08-26 に実際に起きた）
- ⚠️ **検索語を短縮すると `aria-label` から商品名が消える**（`resolveLinks` は aria-label に検索語を使う）

**完了条件**: 測定した語・着地順位・判定の表があり、変更したものは変更前後の順位が両方記録されている。

### `/fix-site` — サイト・ビルドの修正

1. 変更する
2. `npm run build --prefix site`
3. ブラウザで実測（該当箇所のスクリーンショット、または DOM の値）
4. `python tools/check-link-position.py`
5. コミットして push（`main` に入れると Cloudflare が自動デプロイ）

**手順に埋め込む罠**:
- ⚠️ **class 名を変えたら、その class を見ている検査ツールも直す**（2026-08-31 に `toc` → `toc toc--inline` で `check-link-position.py` が壊れた）
- ⚠️ **ブラウザのスクロール後のスクリーンショットは空白になることがある。** 縦長のビューポートで撮る
- ⚠️ **grid の子に `margin-inline: auto` を付けると max-content 幅に縮む。** `width: 100%` を併記する

**完了条件**: ビルドが通り、変更箇所をブラウザで実際に確認した証拠があり、リンク位置が悪化していない。

## 実装しないもの（いま入れない理由つき）

| | 理由 |
|---|---|
| オーケストレーターのエージェント | メインセッションが担う。ルールが明示的に禁じている |
| 記事以外の contract / rubric（測定用など） | **生成と評価の分離が効くのは記事だけ。** 測定に評価者は要らない |
| Hooks による reviewer の書き込み禁止 | Write/Edit を外すところまでで様子を見る。効かないと分かってから足す |
| 並列実行（fan-out） | 目的に入っていない |

---

## この設計が前提にしていること（外れたら作り直す）

- **記事執筆は今後も繰り返す。** 繰り返さないなら writer/reviewer の投資は回収できない
- **ビルドのガードは今後も増える。** 増えたぶんは契約から**外す**（二重化しない）
- **reviewer の落第が実際に品質を上げる。** 上がらなければこの2体構成自体が不要
  → **最初の3本で、reviewer が何件落第させたかを数える。0件なら構成を見直す**
